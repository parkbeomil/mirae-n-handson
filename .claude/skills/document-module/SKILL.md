# 레거시 모듈 문서화

- **분석 대상 폴더(`legacy/<모듈>/`)의 파일은 읽기만 한다.** 수정 · 실행 · 포맷팅하지 않는다.
- 근거는 모두 `파일:줄번호` 로 적는다. 모듈 안 파일은 모듈 경로를 뺀 경로, 모듈 밖 파일은 저장소 루트 기준 경로로 쓴다.
- **단계가 끝날 때마다 결과를 파일로 저장한 뒤 다음 단계로 넘어간다.** 다음 단계는 앞 문서를 선행 문서로 머리말에 적는다.
- **저장 전 점검:** 근거 코드 인용마다 원문 파일의 해당 줄을 다시 열어 글자 그대로 같은지 대조한다. 다르면 고친 뒤 저장한다.
- 문서마다 머리말에 아래 항목을 둔다.
  - 작성일
  - 범위: 다루는 단계를 번호가 아닌 이름(진입점 · 의존 관계 · 데이터 흐름 · 비즈니스 규칙 후보)으로 적는다. 범위 제한이 있으면 함께 적는다.
  - 근거 표기: 위 `파일:줄번호` 경로 규칙
  - 선행 문서: 앞 단계에서 만든 문서(첫 문서는 뺀다)
  - 작성 원칙: 판단 기준으로 삼은 것(예: 주석과 코드가 다를 때의 처리)
- 설정 파일의 비밀번호 · 계정 · 토큰 값은 문서에 옮기지 않는다. 환경 변수 · 설정 키 이름만 적는다.

## 0. 입력 해석

- 인자가 없으면 멈추고 대상 모듈을 묻는다.
- 첫 인자(모듈 경로)를 `<모듈명>` 으로 바꾼다. 폴더 이름을 그대로 쓰지 않는다.
  - `legacy/item-bank-php` → `item-bank`, `legacy/assignment-thymeleaf` → `assignment`, `legacy/grade-mssql` → `grade`
  - 셋 중 어디에도 해당하지 않으면 멈추고 묻는다.
- 둘째 인자(범위 제한)가 있으면 그 범위만 분석하고, 각 문서 머리말 "범위"에 적는다.

## 1. 계획 제시

- 파일 목록만 훑고 2~5단계의 대상 파일 · 산출물 · 제외 범위를 계획으로 제시한다. 확인을 받은 뒤 2단계로 간다.
- 빌드 산출물 · 외부 라이브러리 폴더(`bin/` · `build/` · `target/` · `vendor/` · `node_modules/`)는 기본 제외 범위에 넣는다. `src/` 사본이 있는 `bin/` 같은 폴더를 근거로 쓰지 않는다.

## 2. 진입점 → `docs/<모듈명>/ARCHITECTURE.md`

- 모듈 개요(실행 환경 · 포트 · DB 접속)와 폴더 구조를 쓴다.
- 외부 요청이 들어오는 지점(화면 파일 · 컨트롤러 매핑 · 배치)을 표로 적는다: 진입점 / 파일 / 입력 / 처리 흐름.
- ARCHITECTURE.md 로 저장한다.

## 3. 의존 관계 → ARCHITECTURE.md 에 추가

- 파일 포함 · 함수 호출 · DB 객체 호출을 **호출하는 쪽 → 호출되는 쪽** 방향으로 적고 흐름도(mermaid)를 그린다.
- 가장 긴 함수 3개를 표(파일 / 함수 / 시작~끝 줄 / 줄 수 / 하는 일)로 적는다. 이관 때 먼저 쪼개야 할 후보를 보여 주려는 것이다.
  - 함수 없이 위에서 아래로 실행되는 스크립트는 순위에서 빼고 줄 수와 함께 따로 적는다.
- 미확인 목록을 붙여 저장한다.

## 4. 데이터 흐름 → `docs/<모듈명>/ERD.md`

- 모듈이 접근하는 테이블 · 뷰 · 프로시저를 적는다. 정의(뷰의 WHERE 조건 포함)는 두 곳을 모두 읽는다.
  - `db/<엔진>/init/` 초기화 스크립트
  - 모듈 안 SQL 파일(예: `legacy/grade-mssql/sql/`)
  - 같은 객체가 한쪽에만 있거나 양쪽 정의가 다르면, 어느 쪽을 근거로 썼는지와 차이를 적는다. 실제로 DB에 올라가는 쪽이 코드 · 설정으로 확인되지 않으면 미확인 목록에 넣는다.
- 테이블 관계(mermaid erDiagram + 관계 근거), 테이블별 읽기 · 쓰기 위치, 모듈이 쓰지 않는 테이블, 미확인 목록을 쓰고 저장한다.

## 5. 비즈니스 규칙 후보 → `docs/<모듈명>/BUSINESS-RULES.md`

- 조건문 · SQL 에 있는 것만 규칙으로 올린다. 주석과 코드가 다르면 코드를 기준으로 쓰고 주석은 비고에 남긴다.
- 영역별로 묶고 맨 앞에 요약 표(영역 / 규칙 ID / 개수)를 둔다. 규칙마다 아래 형식을 쓴다.

~~~markdown
### BR-NN
- 규칙: {코드 값 그대로 쓴 한 문장}
- 근거: `파일:줄번호`, `:줄번호`
- 근거 코드:
  ```<언어>
  {주석 기호} 파일:줄번호
  {원문 그대로 인용}
  ```
- 확신도: 확실 | 추정
- 비고: {주석과의 불일치 · 매직 넘버 · 같은 규칙 다른 구현 · 실행 확인 안 함}
~~~

- `{주석 기호}` 는 그 언어의 주석 문법으로 쓴다(PHP · Java `//`, SQL `--`, HTML · Thymeleaf `<!-- -->`).
- 확신도는 인용한 코드만으로 조건과 값이 정해지면 `확실` 로 쓴다. 런타임 입력 · DB 동작(콜레이션 · 제약 등) · 인용 밖 설정에 기대거나 실행해 봐야 알 수 있으면 `추정` 으로 쓴다.

- 끝에 매직 넘버 표와 "규칙으로 올리지 않은 항목"(주석만 있음 등) 표를 붙여 저장한다.

## 6. 사람이 표본 점검할 규칙 3개 추천

- 답변 끝에 규칙 3개를 이유와 함께 추천한다. 하나는 **가장 그럴듯해서 검토 없이 넘어가기 쉬운 규칙**으로 고른다.
- 나머지 둘은 형 변환 · 경계값 · 여러 쿼리가 공유하는 조건처럼 틀리기 쉬운 곳에서 고른다.

## 하지 말 것 (item-bank 분석에서 실제로 틀린 유형 — `docs/item-bank/BUSINESS-RULES.md` §7)

- 조건을 붙인 쿼리 하나만 보고 끝내지 않는다. 같은 WHERE 변수를 쓰는 건수 쿼리 같은 다른 쿼리까지 따라간다.
  - BR-09: `level < 5` 가 건수 쿼리(`search.php:526`)에도 걸린다는 점을 놓쳤다.
- 형 변환 분기는 정규식을 통과하지 못한 값이 변환 뒤 어떤 값이 되는지 확인한다.
  - BR-11: `05` 는 `^[1-5]$` 를 통과하지 못하지만 `(int)` 로 5가 되어 난이도 5 결과가 나온다.
- 뒤쪽 분기 하나만 보고 범위를 일반화하지 않는다. 앞 분기가 먼저 거르는 값이 있는지 확인한다.
  - CX-17: `$page < 1` 만 보고 "0 이하는 경고 없음"이라고 썼지만, 음수는 앞의 `^[0-9]+$` 에서 경고가 붙는다.
- 주석 · 안내 문구의 결과 예측("→ 0건", "대개 0건")을 규칙 문장에 옮기지 않는다. 앱 비교와 DB 비교(콜레이션)가 다르면 결과를 단정하지 않는다.
  - CX-10: 미등록 태그를 "결과 0건"으로 단정했다.
- 모듈이 조회하는 뷰 · 테이블 정의를 읽지 않은 채 "확인 불가"로 남기지 않는다.
  - CX-12 · CX-24: `v_item_public` 의 `status = 'A'` 조건(`db/mariadb/init/01-schema.sql:70`)을 확인 불가로 두었다.
